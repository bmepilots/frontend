# Community contributions

Updated: 2026-10-04. All labels, validation messages and accessibility text in these screens are English. Member-provided text and filenames remain as supplied.

## Feature map and routes

| Area             | Member routes                  | Admin route        | Main source                            |
| ---------------- | ------------------------------ | ------------------ | -------------------------------------- |
| Shared documents | `/documents`, `/documents/:id` | `/admin/documents` | `features/documents/DocumentsPage.tsx` |
| Crew calendar    | `/calendar`                    | `/admin/calendar`  | `features/calendar/CalendarPage.tsx`   |
| Useful links     | `/links`                       | `/admin/links`     | `features/links/LinksPage.tsx`         |

The member and administration screens reuse the same feature components. Every active member sees contribution actions. Edit/delete controls appear for the original author and administrators; document comments have their own author check independent of the post author. These checks guide the interface only. The backend enforces active status, permissions, CSRF and optimistic versions on every operation.

The former Knowledge base navigation has been replaced by Shared documents. `/knowledge/*` redirects to `/documents` and `/admin/knowledge/*` redirects to `/admin/documents`. Existing articles are preserved by backend migration V5 as document posts with their original IDs, full text and authorship; these legacy posts can have zero files. The original knowledge feature source is retained for reference but is not routed. Old article URLs currently lead to the document list rather than the corresponding post detail.

The dashboard uses `/dashboard` fields `documents` and `upcomingEvents` to show recent contributions and approaching calendar entries. Sidebar and admin navigation expose the new areas. No sample posts, uploads, links or events are generated by the UI.

## Shared documents

The list searches titles/descriptions, uses pages of 20 posts and shows author, creation date, file count and comment count. Query keys are `['documents', 'list', search, page]` and `['documents', 'detail', id]`. A mutation invalidates the documents domain and dashboard so counts and recent content update together.

Selecting Share documents opens a native dialog. Files can be selected in several batches and removed individually before submission. `document-files.ts` centralizes the client limits: 1–5 nonempty files, each at most 50 × 1024 × 1024 bytes. The UI calls this 50 MB, matching the backend display convention. Files one byte over the limit, empty files and a sixth file produce English errors before a request. Client checks are feedback only; backend streaming and multipart limits enforce the same rules.

Post creation sends `FormData` to `POST /documents` with `title`, `description` and repeated `files`. The shared API client adds the CSRF header and cookies, and deliberately leaves the multipart Content-Type boundary to the browser. Do not JSON-stringify this payload or manually set its multipart Content-Type. Title is required and limited to 180 characters; description can be empty and is limited to 100,000. Form controls and closing are disabled while the upload is pending. The upload has an indeterminate progress message, not a fabricated percentage.

A detail screen presents the full description as escaped text, authenticated download links and a discussion. Files are not previewed or executed in the page; downloads use `/api/v1/documents/{postId}/files/{fileId}/download` and backend forced-attachment headers. The application never receives a filesystem path in its DTOs.

Anyone can comment. Comments are nonblank and limited to 5,000 characters. The original author remains visible after administrative edits. Post/comment edits carry the displayed version; deletes use a version query parameter. Errors retain the dialog or composer for correction, and stale-write conflicts require reloading the latest data. Deleting a post asks for confirmation because the backend also removes its comments and files. Editing a post changes only title/description; upload a new post for a different set of files.

## Calendar behavior and time contract

The calendar opens at today's date in **Europe/Budapest**, regardless of the computer's timezone. It supports a Monday-first month grid, previous/next month, Today, a selected-day agenda, a whole-month agenda and filters for Exam / test, Event and Homework / deadline. Calendar cells have accessible date/count labels; entry buttons have explicit title/type/time labels. Smaller screens use event dots in the grid with full details in the selected-day list. Color is supplemented with visible type labels.

The API query covers the complete 42-day month grid: `/calendar/events?from=YYYY-MM-DD&to=YYYY-MM-DD`, with an exclusive end date. Its query key is `['calendar', from, to]`. The selected-day list includes events overlapping that date, including overnight entries; the month agenda includes events overlapping the selected month. Mutations invalidate the calendar domain and dashboard.

`startsAt` and `endsAt` are Budapest **wall times**, represented as ISO local date/time strings without `Z` or offsets. They must never be passed through browser-local timezone conversion or the generic UTC activity formatter. `calendar-dates.ts` uses UTC as a stable container for date-only arithmetic, while preserving the entered calendar clock time. The shared `date()` helper is used only for UTC creation/update timestamps.

The event editor accepts title (required, 180 characters), description (10,000), optional location (200), type, start and optional end. A timed entry without an end is suitable for a deadline. Ends must follow starts. The all-day editor deliberately asks for an inclusive Last day; submission converts it to an exclusive midnight end by adding one date. For example, 19–20 October becomes start `2026-10-19T00:00:00`, end `2026-10-21T00:00:00`. Editing reverses that conversion, and display subtracts one date from an exclusive end. A missing end means a single all-day date. Date rules and DST boundaries have dedicated tests.

## Useful links

Every member can add a link through `POST /links`; the current author or an administrator can PATCH/DELETE it. Cards show original authorship. Legacy entries with unknown author display the backend's `Original content` attribution and only administrators can manage them. Category editing remains available in the administration view. Migration V6 supplies General if there were no categories, and the new-link editor selects General where available. When no categories exist, the empty state explains that an administrator must create one.

Link forms match the server limits: name 120 characters, description 500, URL 2048 and nonnegative sort order/version. Browser URL validation provides initial feedback; the server restricts destinations to absolute HTTP(S) URLs without embedded credentials. External links open with `noopener noreferrer`. Query keys are `['links', 'list']` and `['links', 'categories']`; mutations also invalidate the dashboard.

## Audit and safe rendering

Author IDs/names come from the server; the client never supplies a chosen author. Changes and downloads are audited by the backend, so frontend route navigation is not presented as a business audit event. See `../../backend/docs/DOCUMENTS.md` and `../../backend/docs/COMMUNITY.md` for endpoint details, storage, limits and action names. Never log upload contents, descriptions, comments, cookies or credentials in the browser.

All new user content is rendered as React text, not raw HTML. Only the existing Markdown component handles explicitly supported Markdown elsewhere. Uploaded bytes remain in private backend storage. Native dialog cancel events are prevented before the controlled close callback, allowing pending upload/save guards to keep the dialog visible. Revisit this invariant when introducing another modal primitive.

## Verification and extension notes

`document-files.test.ts` checks file count/size boundaries and empty content. `DocumentsPage.test.tsx` exercises multipart member submission, preservation of an in-flight upload after Escape/close requests, and commenting on another member's post without management controls. `calendar-dates.test.ts` covers Monday grids, month/leap-year changes, DST dates, exclusive all-day ends, midnight deadlines and overnight events. `CalendarPage.test.tsx` verifies inclusive-to-exclusive submission and read-only access to another author's event. `LinksPage.test.tsx` checks member contribution, displayed author, hidden peer controls and owner/admin versioned editing.

Component tests use jsdom and a mocked transport; they do not replace backend HTTP/MariaDB tests. Their dialog stubs must toggle `open`, not just count `showModal()` calls, so inaccessible closed dialogs cannot accidentally pass. Actual executed test/build/lint results belong in `STATUS.md`. Browser access was previously denied; no live visual/mobile browser verification is claimed.

Current limits: uploads have no byte-level progress/cancel/resume, existing files cannot be replaced within a post, comments are not paginated, calendar has no recurrence/reminders/external sync and lists use the backend's current bounds. Changes to these contracts must update this document, shared DTOs, relevant feature tests and the backend documentation together.
